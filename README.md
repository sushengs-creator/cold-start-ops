# 冷启动运营顾问 · cold-start-ops

把“社群没人回应”“平台撮合不成”“试点难以复制”变成有依据的瓶颈判断与下一步验证方案。

这是一个可安装到 Codex 的中文运营 Skill，基于 Andrew Chen《The Cold Start Problem》的网络效应框架设计。适合社群、双边平台、协作产品，以及已有用户但增长、留存或竞争出现问题的网络型业务。

**先读 [冷启动方法论](docs/methodology.md)，或直接安装后带着一个业务卡点开始。**

## 最简单的安装方法

在 Codex 中复制下面这句话发送即可。需要 Codex 自带的 `skill-installer` 可用，并允许访问 GitHub。

```text
请使用 skill-installer 安装 GitHub 仓库 sushengs-creator/cold-start-ops 的 Skill。
技能位于仓库根目录，安装参数为 --repo sushengs-creator/cold-start-ops --path . --name cold-start-ops。
如果已经安装，请先检查现有版本和本地修改，不要直接覆盖。
```

安装完成后，在下一轮对话调用 `$cold-start-ops`。如果技能列表尚未刷新，重启 Codex 后再试。

也可以在 macOS 或 Linux 的终端运行这一行，需要已安装 Git。

```bash
git clone https://github.com/sushengs-creator/cold-start-ops.git "${CODEX_HOME:-$HOME/.codex}/skills/cold-start-ops"
```

目标目录已存在时，Git 会停止克隆。请先检查已有版本和自己的修改，不要直接删除。其他支持 `SKILL.md` 的工具，可以将仓库完整放入该工具的技能目录；具体安装位置和调用语法依工具而定。

## 调用口令

`$cold-start-ops` 是在 Codex 对话框里使用的技能名称，后面接自然语言，无需记忆参数。

```text
$cold-start-ops
我们在做【业务】，用户是【角色】，现在遇到【具体问题】。
已有材料是【数据或观察】，可用资源是【人力、预算与期限】。
请先判断网络效应是否适用，找出当前最值得验证的瓶颈，
给出下一步动作、衡量方法和继续或停止的条件。缺证据处标为假设。
```

下面三个口令可以直接改写使用。

**从零启动**

```text
$cold-start-ops
我要做跨境电商运营互助社区，尚未建群，也没有访谈记录。
团队2人，首月预算6000元。请设计候选最小网络、需求验证和首月行动，
明确困难侧用户、首次价值事件、资源上限及扩张条件。假设单独标明。
```

**诊断已有业务**

```text
$cold-start-ops
我们做同城摄影撮合，已有摄影师，但用户经常找不到合适服务。
根据我提供的分城区、时段、需求类型记录，区分供给、匹配与信任问题，
确定优先处理的局部网络，设计一次小范围实验。
```

**复盘实验**

```text
$cold-start-ops
沿用原实验口径复盘下面的计划、执行记录和结果。
区分已支持与尚未验证的假设，给出继续、修改、停止或扩张的决定。
【粘贴原实验卡、数据、资源消耗和异常情况】
```

也可以说“按《冷启动》的网络效应方法，帮我诊断这个社区为什么没人回应”。更完整的扩张、竞争、纯数据分析和评审口令见 [调用示例](references/invocation.md)。

## 你会得到什么

| 你遇到的问题 | Skill 帮你完成的判断 | 主要交付 |
|---|---|---|
| 从零开始，不知道先找谁 | 候选局部网络、关键角色和首次价值 | 需求验证与启动计划 |
| 人已经进来，却没有有效互动 | 供给、需求、匹配、信任或响应的障碍 | 优先瓶颈与实验卡 |
| 一个试点有效，准备扩大 | 哪些条件能复制，哪里尚缺证据 | 扩张顺序与验证条件 |
| 活跃或增长下滑 | 局部网络、用户分组及指标口径差异 | 当前判断与修复方向 |
| 关键用户去了竞争平台 | 实际收益、体验和多平台使用的原因 | 竞争假设与验证方案 |

完整诊断会明确事实、假设、资源约束和下次判断条件。如果你只要一段数据分析或一份计划评审，它会按指定范围交付。

## 为什么值得使用

它把几个容易遗漏的判断固定进流程。

- **先检查适用性。** 多人使用、投广告或一次转发增长，都不足以证明网络效应。
- **看到局部差异。** 按城市、时段、团队或话题检查用户能否得到结果，避免总注册量掩盖问题。
- **把动作接到证据。** 建议需要说明责任角色、资源前提、主指标和下一次决定条件。
- **保留不确定性。** 缺数据时给出假设和采集办法，不捏造留存率、预算或效果预测。

一次已经执行的模拟测试提供了 A 地 30 次请求、24 次成功，B 地 90 次请求、27 次成功。Skill 正确算出整体成功率为 42.5%，指出主要缺口集中在 B，并说明这些数字尚无法确定失败原因。这体现了它对计算和证据边界的要求。[测试记录](docs/validation.md)

它可以帮助团队把讨论推进到可执行、可复盘的方案。实际增长仍取决于需求是否成立、执行质量和真实用户反馈。
